# 議題ワークスペースの画面・判断・実装連携設計

更新日：2026-11-05。今回の「それで設計まとめて」を受けた設計方針。実装済み・実機受入済みという意味ではない。

本書は議題ワークスペースの画面と業務状態の正本とする。[ロードマップ](ROADMAP.md)は進捗と全体の受入、[読取り契約](read-only-app.md)は現行の表示・搬送契約、[設計書](DESIGN.md)は基盤の責務を扱う。本書と異なる過去の画面案を実装の根拠にしない。

## 1. 完成させる体験

一つの開発議題について、参加している名前付き会話を見失わず、やり取りの本文を読み、人間が設計を採用し、その設計に対応する実装と検証を確認できる。

最初の対象は`Codex Desktop`と`Claude Code`の二席。二席は最小の受入範囲であり、データを二席固定にはしない。`Argon`の既存経路は保持するが、今回の画面完成条件を追加モデルへ広げない。既存製品のコードを転用せず、既存の円卓の送信・回収・記録処理を再利用する。

今回の成果は設計の一本化まで。通常導入先の更新、既存チャットへの追加送信、新しいチャットの作成、公開やマージは設計をまとめる操作に含めない。

## 2. 選んだ構成と理由

| 構成 | 得意なこと | 今回の扱い |
|---|---|---|
| 時系列のリレー＋固定した判断欄 | 追加質問の前後関係と、議論から実装への流れを読む | 通常画面に採用 |
| 二回答の横並び比較＋履歴 | 同じ問いへの独立案を比べる | 同じ依頼グループを選んだ時だけ展開 |
| 元の二チャット＋短い決定ノート | 追加開発なしで運用できる | 受入試験の比較対象・手動運用の選択肢 |

前回の「常に二列比較を中心にする」案を変更する。利用者の主目的は一問一答の比較ではなく、会話を続けながら設計と実装を進めることだからである。要約だけの画面にもせず、根拠となる回答本文をその場で読めるようにする。

## 3. 一画面の配置

```text
┌ 議題 ─────┬ 選択中の議題名 ✎ ───────────────────────────┐
│ ＋ 新しい議題│ Codex「会話名」↗       Claude「会話名」↗    │
│ 話題A       │ 回収済み                 回答待ち           │
│ 話題B       ├──────────────────────┬─────────────────────┤
│             │ やり取り             │ 次に決めること       │
│             │ 自分 → 両席：問い    │ 問い・選択肢         │
│             │ Codex：回答本文      │ 判断と理由           │
│             │ Claude：回答本文     │ ［この判断を採用］   │
│             │ ［二回答を比較］     │ 採用設計 v1          │
│             │ 自分 → Claude：…    │ 実装依頼と結果       │
│             ├──────────────────────┴─────────────────────┤
│             │ 宛先：☑ Codex  □ Claude    引用：選択した発言│
│             │ 質問・依頼の本文                            │
│             │                       ［宛先と本文を確認］  │
└─────────────┴────────────────────────────────────────────┘
```

- 左は議題の切替。初期名は最初に登録した会話名を使い、円卓内で編集できる。保存先の`slug`や会話`ID`は変えない。
- 上部の参加席はスクロールしても残す。サービス名、チャット名、今回の依頼状態、元会話への移動を表示する。席をクリックすると宛先候補として選択でき、選択と外部への移動は別操作にする。
- 中央は話者・宛先・本文・判断の時系列。新規議題は空の説明と「参加チャットを追加」、既存議題は未読位置、なければ末尾を開く。読んでいる途中の自動スクロールはしない。
- 右は「次に決めること」「現在の採用内容と理由」「実装依頼・結果」。採用前は「未採用」と明示する。全履歴を読まずに現在地を確認できる。
- 下は一つの入力欄。主ボタンは「宛先と本文を確認」。確認画面で宛先全件・引用元・添える内容・固定した本文を読み、「この内容を送信」で確定する。
- 狭い画面では判断欄を本文の上に畳み、採用版・次の一問の要約は残す。二回答比較は縦に積む。追加の独立ウィンドウや横スクロールを必須にしない。

送信詳細、`JSON`指示、内部`ID`、機械用の根拠表、原本を通常画面のタブにしない。回答の出典や検証結果は読みやすく展開し、診断用の詳細は補助操作から開く。`AI`要約を追加する場合は「`AI`の提案」と本文への参照を付け、元の本文を置き換えない。

## 4. 会話の選択と名前

全会話カタログは「参加チャットを追加」から開く。`Codex`／`Claude Code`を横の切替にし、表示名で検索・並べ替えする。登録済み席と検索候補を混ぜない。

`Claude`の正式なプロジェクト、作業フォルダ、元サービスが明示する親子会話は別の属性とする。正式な所属を取得できた場合だけ「プロジェクト → 会話」の階層を作る。作業フォルダの表示には「作業フォルダ」と書く。未取得の所属やタイトルをフォルダ名から推測しない。同名会話の区別に必要な所属・更新日時は補足表示し、内部では元`ID`を保持する。

議題名、円卓内の席の別名、元サービスのチャット名は別である。議題名・席の別名は円卓内で変更できる。元チャットへの改名反映は、正式な変更経路と実機受入が確認できた接続先だけの明示操作にする。円卓で改名しただけで元アプリも変更済みとは表示しない。

チャット名の索引を読めることは、本文読取り・送信・元会話への移動が可能という意味ではない。席ごとに「閲覧のみ」「手動受渡し」「送信可能」を分ける。`CLI`の新規実行は既存`Desktop`会話と同じ名前付き席を装わず、実行とモデル名を表示する。

## 5. 同時依頼とリレー

同時依頼は同じ問いを選択した複数席に渡す。依頼グループに各席の既存`invocation`を関連付け、送信予約・受付・到達・回収は各席で追う。グループは通信をやり直す新しいキューではない。

リレーは「引用する発言」と「宛先」を選んで追加質問する。例えば`Claude`の回答を引用して`Codex`に聞く場合、引用元は`Claude`、送信先は`Codex`である。未選択の席や会話全文を自動で添えない。本文や宛先を変更した後は、確認済みの旧版を送らない。

最初の依頼は登録済み席から宛先を明示選択する。以後は前回の宛先を候補として残すが、二席目を勝手に追加しない。空の宛先、別議題の席、変更された登録は送信前に止める。

## 6. 人間判断と進行状態

採用、実装依頼、結果の受入を別操作にする。「採用」で議題を閉じない。既存の`close`は全体を終える最終操作として残す。

```mermaid
flowchart LR
  A[問い・参加席] --> B[宛先と本文を確認]
  B --> C[席ごとに送信・照合・回収]
  C --> D[本文を読み追加質問]
  D --> B
  D --> E[人間が理由付きで採用 v1]
  E --> F[実装先と範囲を確認して依頼]
  F --> G[対応する差分と検証を回収]
  G --> H[人間が結果を受け入れる]
  E --> I[判断変更 v2]
  I --> F
```

上の図は業務の流れであり、単一の完了フラグにはしない。

| 軸 | 表示する状態と証拠 |
|---|---|
| 席ごとの依頼 | 準備済み／受付確認／到達確認／回答待ち／回収済み／到達未確認。既存の`journal`と受領記録から表示し、稼働中とは推測しない |
| 設計判断 | 未採用／採用`v1`／後の版で置換。人間が選んだ本文・理由・根拠回答を保持する |
| 実装依頼 | 未依頼／引継ぎ確認／実行確認／結果回収／人間受入。送信受付だけで実行中にしない |

自動で進めるのは許可済みの到達照合、回答回収、証拠に基づく表示。人間が決めるのは送信範囲・採否・実装の許可範囲・判断変更・結果の受入。既存の承認範囲を引き継ぎ、段階ごとに同じ許可を聞き直す仕組みを増やさない。`AI`の一致や推奨文は採用記録を作らない。

| 例外 | 画面と動作 |
|---|---|
| 到達未確認 | 「到達を確認」「元会話を確認」。再送せず照合する。文面変更や別経路への切替を安全な再送の代わりにしない |
| 一席だけ未回答 | 回答済み本文を読める。未回答を固定表示し、その状態で採用する場合は人間が確認した事実を残す |
| 一席だけ送信成功 | 成功席は再送しない。もう一席の未送信・未確認を区別する |
| 判断を変更 | `v2`を追加。`v1`と過去の結果は保存し、「実装は`v1`に対応／`v2`未反映」を表示する |
| 結果に検証不足 | 「結果報告あり・検証未確認」。エージェントの成功報告だけで人間受入へ進めない |
| 読取り不整合・旧形式 | 「状態未確認」。表示の再読込みは送信や修復を起動しない |

## 7. データの正本と既存処理の再利用

ソース外の明示した`Git`管理`ROOT`と、既存の議題ディレクトリを使う。新しいデータベース、常駐サービス、並行する決定台帳は作らない。

| データ | 所有先と変更方針 |
|---|---|
| 席の元`ID`・表示名・接続方法 | 既存`seats.json`。所属と親子は出典付きで確認できた属性だけ追加 |
| 依頼・受付・到達・回収 | 既存`journal.json`の`invocations`、受領記録、既存の固定`packet`・`snapshot`・回答。送信予約と照合を作り直さない |
| 人間の採用・採用版・引継ぎ・結果受入 | 既存`journal`の`human_actions`へ型を持つ追記記録を追加。業務記録の正本とし、本文の語句から採用を推測しない |
| 人間向けの議事録 | 既存`minutes.md`の回答・判断表示。新しい判断記録は記録`ID`を使って重複なく反映。既存の自由記述判断は履歴として保全 |
| 現在の採用版・次の一問・実装との対応 | 上記の記録から表示用に導出。別の可変な状態ファイルを正本にしない |

追加する業務記録の最小形は、記録`ID`、操作種別、時刻、対象議題、参照する記録`ID`、操作固有の内容。採用は判断本文・理由・根拠回答・置換前版、引継ぎは採用版・実装先・対象範囲・受入条件・依頼`invocation`、結果は引継ぎ・対応する固定コミット／差分・検証結果・確認範囲を保持する。`UI`の状態ラベルや経過時間は保存しない。

例：従来の「座長判断：照合のみ」という自由文だけの記録から、採用`v1`に判断本文、理由、`Codex`と`Claude`の回答参照を付け、実装依頼がその`v1`を参照する形へ進める。人間の操作という分類はアプリ上の記録であり、機械署名や本人認証の新保証ではない。

保存は既存の`Git`検査・短い排他・原子的置換を再利用する。採用では期待する直前版をロック内で比較し、別ウィンドウの採用が先行していれば再確認に戻す。既存`record_human_action`を呼ぶだけではこの版競合を防げないため、検査と追記を同じ書込み区間にする。

`journal`を先に確定し、議事録反映は同じ記録`ID`で再実行可能にする。二ファイル同時確定を保証したふりはしない。途中停止では「判断保存済み・議事録反映待ち」とし、再表示時に読取りだけで修復せず、明示した回復処理で反映する。同じ`ID`の異なる内容、参照先の欠損、並行した採用版の分岐は競合として扱い、後勝ちで上書きしない。

旧データにない採用版は補完しない。旧`journal`の読取りと既存`export`形式を保持し、新しい読取り項目は版付きで追加する。最新の採用本文を過去の固定`packet`へ差し込まない。

## 8. モジュールの責務

| 所有先 | 役割 |
|---|---|
| `app.py` | 一画面の配置、選択、入力、プレビュー、表示。送信プロトコルや判断の保存規則を埋め込まない |
| `app_actions.py`と既存`CLI` | 準備・確認・送信・回収・採用・実装依頼の入口。同じ操作を`GUI`と`CLI`で重複実装しない |
| `journal.py` | 記録の検査と併合、直前版を確認した人間操作の追記。既存の送達記録を保持する |
| `minutes.py` | 回答の既存回収と、人間向け判断の重複しない反映。採用と議題終了を分ける |
| `read_model.py` | 記録から参加席・時系列・現在の採用・実装結果を投影。読取り中に通信、ロック作成、修復、送信を起動しない |
| 既存の`Codex`／`Claude`搬送 | 宛先固定と送信、到達照合。`Codex`公式キューと再送しない回収を再利用する |
| `Safe Resume` | 利用枠中断と再開。円卓は観測を表示し、円卓の送信を再開処理で重複投入しない |

実装用の入口は「記録を読む → 操作の期待版と参照を検証 → 一件の操作を保存 → 表示へ投影」とする。全面的なフレームワーク移行や新しいエージェント実行基盤はこの設計の前提にしない。

## 9. 実装順と受入

| 単位 | 実装する差分 | 合格を確かめること |
|---|---|---|
| 1. 読める一画面 | 参加席固定、本文中心の時系列、宛先欄、判断欄の配置。既存の実回答または架空データを使う | `Mac`で議題・参加二会話・次の判断が同時に読める。検索は追加時だけ。`Windows`も同じ固定候補を実機確認 |
| 2. 判断の保存 | 構造化した人間操作、採用版、根拠参照、版競合、議事録反映 | 再起動で判断が戻る。`AI`回答は採用にならない。同時採用、重複操作、途中停止で履歴を壊さない |
| 3. 一巡の壁打ち | 既存二席の同時依頼と引用リレー、通常プレビューからの送信・回収 | 専用席で宛先と本文を確認。`Claude`も同じ一連を実機受入。未受入中は手動と表示。到達不明で再送ゼロ、回収重複ゼロ |
| 4. 実装と結果 | 採用版に固定した依頼、対象作業ツリー、差分・検証・受入の対応 | 実装依頼がどの版か分かる。`v2`採用後も`v1`の結果を取り違えない。手動の結果登録は手動と表示 |

小さく使って確かめる題材は「送達不明なら再送するか、照合だけにするか」。二案を読み、対立点を一席へ追加質問し、人間が理由付きで採用し、その判断の小さな実装差分と検証を戻す。既に実装済みの挙動を新規実装したことにはしない。

似た規模の実議題を、既存二チャット＋ノートと新画面で扱う。宛先の取り違え、原文探索の操作、判断の転記、判断と差分の対応漏れを記録する。途中再開時は画面を見て説明してよく、暗記や根拠のない秒数で合否を決めない。題材差と慣れを記録し、少数試行から優位を一般化しない。

つまずきは、画面だけの問題、参照データの問題、搬送の問題に分けて各所有先へ戻す。同じ受入条件をもう一度確認する。接続先を増やすことで未達を隠さず、通常の二チャット運用より判断を復元しやすくなったかで次の開発を選ぶ。

単体試験は競合・重複・版と結果の対応を中心とし、低影響な表示文言だけの試験を増やさない。実際の`GUI`、専用実席の往復、両`OS`、配布、正式統合の受入は別々に残す。

## 10. 根拠と未確定事項

本方針は利用者の「議事録本文が主」「参加チャットが見える」「人間の判断から開発を進める」という要求を優先したもの。文章要件による再レビューで`ChatGPT`・`Claude`・`Grok`・`Sakana`から具体案を回収し、`Gemini`は有効回答なし。多数決や競合への未確認の推測は採用根拠にしない。

現行実装との対応は`app.py`、`app_actions.py`、`read_model.py`、`Journal.record_human_action`、`minutes.add_chair_note`／`write_verdict`を確認した。自由文の座長判断と、議題を閉じる最終裁定は存在するが、本書の構造化した採用版と実装連携は今後の変更である。

未確定なのは、`Claude`の同じ一連の実機信頼性、元会話への移動・改名の接続先別対応、実画面での読みやすさ。手動経路と未確認表示を残し、確認済みと装わない。`Kanary`等への移行可否は本書だけでは決めない。
