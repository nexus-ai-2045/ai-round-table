`integrity.verify_and_read` / `write_verified` の呼び出し元は 3 モジュールに閉じる:

| 呼び出し元 | 対象ファイル | 置換後 |
|---|---|---|
| `journal.py` load/save | journal.json | require_clean → 素 read / atomic write + commit |
| `minutes.py` read/merge | minutes.md | 同上 (MinutesTamperedError は維持) |

付随: `paths.py` (integrity property + docstring)、`cli.py`

## Phase 構成

### Phase 1: `ledger.py` 新設 (git 一本化の核)

- `ensure_git_root(root)`: root が git work tree 内か検査。なければ `git init`
  (new-topic 時のみ。既存議題の操作では検査だけして、外なら fail-closed)
- `require_clean(root, path)`: `git status --porcelain -- <path>` が非空なら
  `LedgerDirtyError` に diff 要約を添えて停止 (fail-closed)。
  **dirty = dispatcher 以外の書込** という不変条件がここで効く
- `commit(root, path, message)`: pathspec 限定 add + commit
  (`git add -A` 禁止ルールと整合。message は `minutes(<slug>): <op>`)
- witness の pending/adopted 巻き戻しは不要 (git が持つ)

### Phase 2: 呼び出し置換

- journal / minutes / relay の read: `require_clean` → 素の read
- write: atomic write (`atomicio` 維持) → `ledger.commit`
- `paths.py`: `TopicPaths.integrity` / `witness()` 削除。`lock()` は `.locks/` 配下へ
- `cli.py`: grok 警告 (`_warn_if_integrity_detection_does_not_hold`) 削除
- `integrity.py` 削除。`StateTamperedError` 基底は ledger.py へ移設
  (`MinutesTamperedError` の継承関係とメッセージ資産は維持)

### Phase 3: テスト移行

- tamper 系: create (auto-commit 済) → minutes.md を直接改変 → merge →
  `MinutesTamperedError`。**検知原理が変わっても守る性質 (fail-closed) は同じ**
- 並行系: FileLock ベースの検証はそのまま。witness 前提の assert だけ落とす
- 新規: (a) root が git 外 → new-topic が init する / 既存操作は停止
  (b) dispatcher commit の pathspec が topic 外に触れない
- tmp root は各テストで独立 repo になるので index.lock 競合しない (要実測)

### Phase 4: 運用切替

- `.gitignore`: `minutes/tier1-final/` を外す / `.integrity/` → 削除猶予 1 commit /
  `.locks/` を追加
- `minutes/tier1-final/` を commit (Tier1 実証を履歴に固定)
- doctor に `git_available` / `root_in_work_tree` 検査を追加
- 2 席 live smoke (codex + grok Tier1) で KPI ≤ 3 を実測

## Phase 2 実装中に確定した設計判断 (2026-08-10)

| 論点 | 判断 | 理由 |
|---|---|---|
| 同一 repo への並行 commit (journal と seats は別 FileLock) | `_git_locked`: index.lock 競合は backoff 再試行 (20 回 / 最大 0.5s) | 排他に負けた = 一時的。失敗にすると並行 dispatch が偶発的に落ちる |
| 読み取り系 git が index を触る | 全 git 呼び出しに `--no-optional-locks` | status の index refresh が書き手と競合するのを根から絶つ |
| enclosing repo で root が ignore されている | その repo は証跡にならないので **独立 repo を init** | .pytest-tmp 配下のテスト root が実 repo に commit する事故を構造的に防ぐ (実際に踏みかけた) |
| 旧 witness の「既存ファイル採用 (adopted)」 | **廃止**。dispatcher の commit が無いファイルは dirty | 採用するかは機械でなく CEO が決める (D1)。自動採用は出所不明を白く塗る |
| 旧 witness の「書きかけ自動復旧 (pending)」 | **廃止**。crash 窓も dirty として CEO に出す | 「自分の書きかけ」と「席の書換」はローカル痕跡で区別できない。勝手に倒すと検知が消える |

## 予測と手当て (MPC)

| 予測 | 手当て |
|---|---|
| dispatcher auto-commit が人間の commit 粒度と混ざる | message prefix `minutes(<slug>):` で機械 commit を判別可能に |
| 席が git 履歴ごと書き換える | ローカルでは可能 (制御外)。**origin へ push した履歴が最終証跡** — 席に credential を渡さない |
| root がネスト repo になる | enclosing work tree を優先して使う。init は「どの repo にも属さない」時だけ |
| git 不在環境 | doctor で検知。ツール要件に昇格 (もともと repo 運用前提) |
| pytest 並走で commit 競合 | root ごとに独立 repo。Phase 3 で実測確認 |

## 既知の負債 (Phase 2/3 実測で確定)

**journal の保存 1 回 = git commit 1 回のコスト** (Windows 実測 ~0.1-0.3s/op):

- 実運用への影響: dispatch 1 回あたり保存 ~7 回 ≈ 2s / 900s — 無視できる
- テストへの影響: 全 suite 5 分 → **約 22 分**。ストレステストは 8x10 連打が
  join 枠を食い切り偽の失敗を出したため 4x5 に縮小 (性質は維持)
- 改善候補 (順に軽い): (a) refresh の clean 検査を省く読取高速経路
  (b) CLI 操作 1 回ごとの batch commit (要: 自分の未 commit 変更を clean 扱いに
  する仕組み — witness の再発明にならない形の設計が必要)
  (c) journal を append-only event log 化 (fix_options B / 従来から backlog 済)
- 判断: v0.3 では (無理に) 直さない。正しさ優先で per-save commit のまま。
  suite が開発の律速になった時点で (a) から着手
