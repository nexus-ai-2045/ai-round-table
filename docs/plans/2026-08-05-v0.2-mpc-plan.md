# v0.2 設計 — MPC 予測 + FDE 次元圧縮

- 日付: 2026-08-05
- 手法: 最適制御の MPC 的 rollout で「次に何が壊れるか」を先に予測し、
  FDE 的に潜在軸へ射影して次元の呪いを回避する
- 前提: v0.1 merge 済み (33 tests green) / backlog 12 件 (L1-L9 + S1-S3) / 実使用 0 回

## 1. 問題設定 (制御問題として書く)

| 記号 | 中身 |
|---|---|
| 状態 x | v0.1 実装 + 未修正の穴 12 件 + **実運用実績 0** |
| 制御 u | 次に作るもの (backlog のどれをどの順で) |

壊れても再実行できるため。

## 2. MPC rollout — ホライズン 3 本の予測

コスト重み: 発生確率 × 損失。「使われなくなる」は損失 = 全損として扱う。

| step | 予測される事象 | 該当 backlog | 確率 | 損失 | 寄与 |
|---|---|---|---|---|---|
| 議題 1 | 貼り付け忘れ / 席が散文を返す / 背景が書けない | S1, S3, L6 | **高** | 中〜全損 | **最大** |
| 議題 2 | 2 席目で round が進まない (部分指名) / close の穴 | L7, L4 | 中 | 中 | 中 |
| 議題 3 | slug 衝突・状態逆行・schema 経路の未検証 | L5, L3, L8 | 低 | 小〜中 | 小 |
| 全体 | **手数が多くて使わなくなる** | S3 + Tier3 全体 | **高** | **全損** | **支配項** |

**予測の結論**: 3 本先まで転がすと、個々のバグより先に「手数」で死ぬ。
→ 制御は手数の削減に打つべきで、backlog の消化順ではない。

## 3. FDE 次元圧縮 — 12 次元 → 4 軸 → 主軸 1 本

12 項目を独立タスクとして扱うと組合せが 2^12 に膨らむ (次元の呪い)。
潜在軸へ射影する:

| 軸 | 意味 | 吸収する項目 |
|---|---|---|
| **A. 手数** | 人間が触る回数 | S2, S3, S1(一部) |
| B. 回収の頑健性 | 席が想定外を返した時の挙動 | L2, L6, L8, S3 |
| C. 状態の正しさ | journal / minutes の状態管理 | L1, L3, L4, L7 |
| D. 境界 | 入力検証・多層防御 | L5, L9, S1(一部) |

**軸間に支配関係がある**: A を Tier1 で潰すと、B の一部が構造ごと消える
(構造化 API で受け取るので「散文が返る」「BOM」「貼り忘れ」が発生しない)。
C と D は A の解決後も残るが、**発生前に検知できれば損失は小さい**。

→ **v0.2 = 軸 A に全振り。B/C/D は「直す」のではなく「検知器を置く」だけ。**
これが次元の呪いの回避 — 12 の独立タスクを **1 本の主軸 + 3 個の detector** に畳む。

FDE の再帰構造 (各軸に同じ判断テンプレを当てる):

| 軸 | Principle | Invariant | Detector | Repair Path |
|---|---|---|---|---|
| A | 人間は判断だけする | 1 議題あたり人間の操作 ≤ 3 | 操作回数を journal に記録 | Tier1 relay |
| B | 席の出力は信用しない | 契約外は必ず failed 記録 | 失敗分類の統計 | v0.3 で分類細分化 |
| C | 状態は前進のみ | merged からの逆行なし | set_state で遷移検証 | v0.3 |
| D | dispatcher は topic 配下しか触らない | 書込パスが topic 配下 | slug 検証 + 書込パス assert | v0.3 |

## 4. 制御則 (v0.2 の中身)

### Phase 0 — spike (不可逆性ゼロ・所要 2h・go/no-go)

Codex 席の Tier1 を実測する。**これが MPC の「1 手だけ打って再観測」に当たる**。

1. `codex app-server` を自前 spawn し stdio JSONL で `initialize` → `initialized`
2. `thread/start` → `thread/name` で `rt-<議題>-codex` を設定
3. `turn/start` で packet 本文を送る
4. **CEO が Codex アプリを開き、その thread が見えるか / 発言が読めるか確認**
5. 席が scratch へ JSON を書けるか (fs API 併用の可否も観察)
6. 撤収 (プロセス終了)

- **go** → Phase 1
- **no-go** → Phase 1' (Tier3 のまま軸 A を削る: `--background` / ack ファイル / 1 コマンド化)

参照: `references/codex-app-server-README.ja.md` (全文訳)、
`.repos/external/codex-client` (Node 参照実装の 2 層構成)

### Phase 1 — Tier1 relay (Codex 席)

- `roundtable/relay.py` に **1 契約のみ**の interface を切る:
  `send(seat, text) -> None` / `poll(seat) -> str | None`
  ACP が 4 者に揃った時点で実装を差し替えられるようにする (DESIGN v6 §4)
- `relay_codex.py` が app-server stdio を実装
- seats.json に `tier` と `thread_ref` を保存
- **Tier1 障害時は自動で Tier3 に縮退**し、その旨を表示 (勝手に Tier2 へ昇格しない)

### Phase 2 — detector のみ設置 (修正はしない)

軸 B/C/D は v0.2 では**壊れたら気づける状態**にするだけ:

- `journal` に `human_actions` カウンタ (軸 A の KPI 計測 = 受け入れ基準の実測値)
- `set_state` に遷移表を入れて逆行を `ValueError` (軸 C、5 行)
- `ensure_topic` で slug を `[a-z0-9-]+` に検証 (軸 D、3 行)
- 失敗分類の集計を `status` に表示 (軸 B)

### Phase 3 — 実議題 3 本 → 再計画

MPC の再計画点。3 本回した実測 (手数・失敗分類の分布) で v0.3 の軸を決め直す。
**ここで backlog を機械的に消化しない** — 観測されなかった穴は優先度を下げる。

## 5. 受け入れ基準 (KPI を 1 本に絞る)

> **1 議題あたりの人間の操作 ≤ 3**（議題宣言 / 指名 / 裁定）

- 貼り付け・コマンド実行・確認クリックはすべて「操作」として数える
- journal の `human_actions` で**機械的に計測**する (自己申告にしない)
- Tier3 席が混ざる場合はその席の分だけ +1 を許容し、内訳を記録

副次条件 (満たさなくても v0.2 は成立):
- 実議題 3 本が完走し、議事録が契約どおり
- 失敗が隠れず記録・提示される (v0.1 から継続)
