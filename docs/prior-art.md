# 先行事例と、この repo の立ち位置

調査日: 2026-09-01。公開前の裏取りとして実施した。
**「既存で代替できないか」を先に確かめる**ためのもので、優位性を主張するためのものではない。

DESIGN v6 は「先行事例ポジショニング」を非公開の内部調査に依っていた。
公開 repo からその参照は辿れないので、公開できる形に置き直したのがこの文書。

## 結論

**3 軸を同時に満たす既存 OSS / 製品は見つからなかった。** ただし
**代替不能なのは組み合わせであって、個別要素ではない。** 個々の要素にはそれぞれ先行事例がある。

| 軸 | 内容 | 先行事例 |
|---|---|---|
| (a) | 席 = 既存チャットアプリのセッション（API キー不要） | **ある**（ただし全て UI 自動化） |
| (b) | 人間が裁定者。自動で合意させない | **ある**（部分的） |
| (c) | git 管理の議事録が唯一の成果物 | **見つからなかった** |

(c) が最も差が大きい。「複数 AI の席」という概念と「git 正本」を両方持つものは確認できなかった。

## 近いもの

### axtonliu/ai-roundtable（MIT / 287 stars）— 最も近い

思想が 2 点でほぼ同じ。

- 「API ではなく web UI を意図的に叩く」。理由も同じで、API と web chat では
  モデル変種・隠し設定・サンプリングが違うため
- 自動モデレータを置かず、人間がファシリテータとして `/mutual`（相互レビュー）や
  `/cross`（指名評価）を打って進行する

決定的な差は 2 つ。**Chrome 拡張による DOM 自動化**（本 repo の Tier2 相当で、ここでは
明示承認なしには使わないと決めている経路）であること。そして保存が `chrome.storage.local`
のみで、**議事録が git に残らない**こと。

<https://github.com/axtonliu/ai-roundtable>

### karpathy/llm-council

3 段階（個別回答 → 匿名相互ランキング → Chairman による統合）。
**座長が AI** で、OpenRouter の API キーが必須。成果物はローカル JSON。
作者自身が「サポートしない土曜の hack」と明記している。

<https://github.com/karpathy/llm-council>

### MassGen（Apache-2.0 / 1.1k stars）— 思想的な対抗馬

複数の frontier モデルと CLI エージェントを並列に走らせ、**エージェント同士の投票**で
勝者を決める。バックエンドは API キー方式と **CLI subprocess 方式**のハイブリッド。

本 repo が設計上禁じている 2 つ（subprocess 実行 / 自動合意）を、そのまま中核に据えている。
どちらが正しいという話ではなく、**同じ問題に対する反対側の解**として読むのが正確。

<https://github.com/massgen/MassGen>

### 円卓会議 プラグイン（note inc. CDO 宇野雄氏）— 日本語圏で最も問題意識が近い

単一モデル内のペルソナではなく独立セッションを並列実行し、Devil's Advocate を必ず参加させ、
少数意見を構造的に保護し、最終判断は人間に残す。問題意識はかなり重なる。

差は席の実体で、こちらは Claude Code のサブエージェント。別 AI アプリの実チャット
セッションではない。

<https://note.com/saladdays/n/nd62af8015341>

### 既存 framework の human-in-the-loop

LangGraph の `interrupt()` / AutoGen の `UserProxyAgent` / CrewAI の `human_input` は、
いずれも**承認・却下・編集のチェックポイント**であって、
「複数 AI の対立意見を人間が裁定する」構造ではない。
AutoGen の UserProxyAgent が最も座長に近いが、席は API クライアント経由のモデルで、
既存チャットアプリのセッションではない。

### SaaS

round-table.ai は 4 プロバイダ 13 モデルをサーバ側認証で束ね、secretary agent が要約し、
人間を decision-maker に置く。API キーは不要だが月額 $30〜$200 で、
**「普段の課金のまま動く」というコスト構造とは別物**。
ChatHub / Chorus 系のマルチモデル並列チャットは「同じ質問を横並びで比較する」道具で、
席同士のレビューや議事録の正本化は扱わない。

## 人間裁定を残す設計への外部的な裏付け

「AI 同士を自動で合意させる」路線は Du et al. 2023（<https://arxiv.org/abs/2305.14325>）が起点。
その後 2025–2026 の研究で consensus の病理が繰り返し報告されている
（バイアスの伝播 / 立場の均質化 / 事実の脱落）。

ただしこれは**設計判断の傍証であって、本 repo の有効性の証明ではない**。
[review-backlog](review-backlog.md) に記録したとおり、この repo は一度、
論文の数値を読み違えたまま設計の権威付けに使っている。同じ轍を踏まないよう、
ここでの引用も「そういう報告がある」以上には使わない。

## この調査で分からなかったこと

- **Tier1 が前提とする「各 AI アプリの公式 API で既存チャットセッションに直接投げる」経路の
  先行事例は 0 件だった。** そのような公開 API が他社にも実在するかは未確認。
  「先行事例が無い」のか「探索語彙が届いていない」のかを切り分けられていない
- 「クリップボード貼付を第 1 級 Tier として設計」「人間の操作回数を KPI として機械記録」も
  先行事例が見当たらなかったが、**不在の証明ではない**
- CrewAI / ChatHub / Chorus は検索結果の要約経由で、製品ページの直接取得をしていない
