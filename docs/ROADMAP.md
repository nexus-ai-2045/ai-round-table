# 責務・完了条件・ロードマップ

この文書は、既存の`AI`アプリ席を使う`Mac`優先の運用を再現可能にするため、このリポジトリの責務と完了条件を定めます。現在の証拠が確認できていない項目は、過去の記録や報告だけで完了にしません。

## 今回のゴール

人間が指定した既存アプリ席へ、固定した依頼を一度だけ渡し、同じ依頼に対応する最終回答を検証して回収できる状態を目指します。中断や回答境界が曖昧な場合は、成功・失敗を推測せず、状態を保全して照合します。

`CMUX`は廃止対象です。今後の必須運用経路・受入基準・新規接続先に含めません。過去の`CMUX`試験記録は当時の証拠として保持します。共通ハーネスと実行設定の正本は`Projects`共通基盤側に置き、このリポジトリへ複製・移管しません。

## 完了条件と確認方法

各項目は、記載した一次証拠を現在の固定`SHA`・対象席・実行記録と結び付けて確認した後にのみ「確認済み」へ更新します。候補版の確認結果は末尾に記録し、正式統合・通常導入の完了とは区別します。過去の検証記録は候補証拠への案内であり、現在の実装・配布物・実席状態を証明するものではありません。

| 必須条件 | 判定に必要な証拠 | 確認手順 |
|---|---|---|
| 変更をレビュー可能な状態で統合する | 対象`PR`と`SHA`、レビュー解決状態、必要な`CI`結果 | `PR` #9・#12・#13は統合済み。現在の候補`SHA`と比較元を固定し、新しい差分のレビュー・必要な`CI`結果を照合する |
| 固定した配布物を`checkout`外から再現して起動する | `Python`版、固定されたビルド・依存入力、`wheel`の`SHA256`、導入先の記録、`checkout`外の`CLI` `smoke`結果 | 固定入力から`wheel`を作り、通常`CLI`として導入して、ソース`checkout`外で起動する |
| 運用データをコードから分離する | `checkout`外の明示`ROOT`、そこで作成・回収した`topic`、ソース`repo`に運用データが増えない確認 | 通常運用では外部`Git` `ROOT`を指定する。既存の追跡済み`minutes/`は監査と保全計画が済むまで移動・削除しない |
| 既存アプリ席へ固定依頼を送り、対応する最終回答を一度だけ回収する | `invocation`と席の対応、依頼・回答の`hash`、最終回答境界、議事録への反映、同一依頼の再回収結果 | 送達、回答完成、検証、回収を別々に記録し、再回収で回答が重複しないことを確認する |
| 後続入力があっても、確認済みの最終回答を正しく保持・識別する | 後続入力前後の席識別子・回答`ID`・内容`hash`と、同一回答の読戻し | 後続入力による最新応答との取り違えがないことを確認する |
| 最終回答より前の中断を曖昧状態として扱う | 中断時の記録、未確定状態の保持、再送・誤回収が起きない確認 | 最終回答の成立を証明できない中断は送達・完了を推測せず、同じ`invocation`の状態照合へ戻す |
| `hook`から拒否された候補を採用しない | `hook`の拒否結果と対象候補の対応、議事録・成果物が変更されない記録 | 拒否理由を保持し、候補を回答として採用しない |
| 回収・再実行が一度だけの結果に収束する | `journal`状態、回答`hash`、議事録差分、同じ`invocation`での再回収記録 | 重複回収で議事録・通知・返却が重複しないことを確認する。送達不明な依頼は自動再送しない |
| `CMUX`を現行運用と受入条件から退役させる | `README`・`CLI`・運用文書の現行説明が一致し、`CMUX`が必須経路として案内されないこと。過去の証拠は履歴として識別できること | 歴史記録を消さずに現在の採用範囲を分け、実装の残存状態も明示する |

必須条件すべての証拠が揃った時に全体完了とします。資料の存在、コマンドの終了コード、貼付報告、過去の実測だけでは、現在の統合・配布・実席運用を完了扱いしません。

## 責務と境界

| 担当・保存先 | 所有する責務 | 境界 |
|---|---|---|
| `ai-round-table` | 依頼`packet`、`invocation`、回答検証、議事録・`journal`、回収・再回収、`CLI`、製品試験と文書 | 共通ハーネス、グローバル設定、`hook`、席の起動・ローテーションを所有しない |
| `Projects`共通基盤 | 複数製品で使うハーネス・席解決・共有`hook`や設定の正本と配布 | この`repo`は参照側。複製して独自の正本を作らない |
| 運用`ROOT` | 議題ごとの議事録・`journal`・依頼・回答と実行状態 | ソース`checkout`外にある、指定された`Git`管理`ROOT`を使う。履歴・保全を確認せず既存データを移動・削除しない |
| 人間の座長 | 議題・参加席・裁定・続行・中止の判断 | `dispatcher`や`hook`が自動で結論を出さない |

運用データの保存先は`CLI`の`--root`で明示します。通常運用の`ROOT`をソース`checkout`内に置かないでください。既存の追跡済み`minutes/`は履歴を含めて監査し、保存先・所有者・移行単位・照合証拠を決めるまで現状保全します。

## 再現可能な導入と運用

完了判定では、ソース`commit`、`Python`版、依存解決・ビルド入力、`wheel`の`SHA256`を一組で記録します。同じ固定入力から作った`wheel`を通常`CLI`へ導入し、`repo`外の作業ディレクトリから`--help`と無害な`CLI` `smoke`を実行します。配布版と統合済みソースの対応を照合し、`editable` `install`や一時`worktree`への依存がないことを確認します。

実席の受入試験は、所有者が指定した既存アプリ席と外部の専用`ROOT`で行います。依頼固定、送達結果、回答の最終境界、回答`hash`、検証・回収、同じ`invocation`の再回収を記録します。最終回答前の中断、後続入力、`hook`拒否を負のケースとして確認し、曖昧な結果は成功へ読み替えません。

## 進める順序

1. **現行状態を固定する**：`PR` #9・#12・#13の統合済み実装を基準に、現在の候補・比較元・必要な`CI`結果を照合する。過去の候補試験を、新しい差分の検証へ読み替えない。
2. **文書と廃止境界を揃える**：`CMUX`を現行経路から外し、履歴資料には過去の記録であることを明記する。共有ハーネス・設定の所有先を外部正本へリンクする。
3. **データ分離を検証する**：新規`topic`を`checkout`外の外部`Git` `ROOT`に作成し、`CLI`操作・回収後も製品`checkout`に運用データが増えないことを確認する。既存`minutes/`は監査・保全を別単位で行う。
4. **ビルドと`CLI`を固定する**：依存入力と`Python`版を固定し、`wheel`を構築・`hash`記録・導入して、`checkout`外の`CLI` `smoke`を実行する。
5. **既存席の完了・回復を確認する**：最終回答、後続入力、最終前中断、`hook`拒否、再回収を同一`invocation`契約で確認する。証拠を結果表へ戻し、未達項目があれば該当段階を継続する。

## 今回の対象外

次の項目は今回の完了条件に追加しません。必要になった場合は、別途目的・担当・証拠を定めます。

- 無人の定期実行・常設`scheduler`
- 任意の`AI` `CLI`を起動する機能
- ホスト`AI`や席を自動ローテーションする機能
- 新しい参加`AI`、4席同時運用、汎用マルチホスト化
- 共有`hook`・権限・認証・モデル設定のこの`repo`からの変更

## Codexの受付と回答回収の区別

`Codex`の`Tier1`は、指定した`threadId`への`turn/start`応答に有効な`turn.id`がある時だけ、受付を確認したと扱います。既存の`journal.json`の対象`invocation`へ、`submission_receipt`として`provider`・`thread_id`・`turn_id`・`status: accepted`を保存します。後の依頼で上書きされる席情報へは保存しません。

受付の記録は、アプリでの表示、実ユーザーメッセージの履歴照合、回答完成の証明ではありません。回答は従来どおり`invocation_id`・`participant`・回答形式を既存の回収処理で照合してから議事録へ反映します。応答が欠ける、不正、または通信が不明な場合は`delivery-unknown`とし、自動再送や`Tier3`への重複投入をしません。受付番号だけで`merged`へ進めません。
